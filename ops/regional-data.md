# Regional data freshness and publication links

The daily directory runner leaves this feature off unless its private state directory contains `regional-data-config.json` with `{"enabled":true}`. Install no new service or timer. After the regional-data migration, source review, initial load and separate operational authorization, place that private file in the existing daily service's state directory; the existing timer will use it on the next run. Remove the file or set `enabled` to false to disable it. Do not enable it merely by merging these files. Missing schema or configuration is safe.

The checker reads loaded regional listings directly, including hidden listings, and excludes removed IDs. It checks the canonical landing URL when it is bound to reviewed evidence. URLs must use HTTPS and an explicitly approved public host; redirects are limited to the original host, and DNS addresses must be public. The generic user agent is `valley-desk-research/1.0`. Landing checks use HEAD, falling back to a bounded Range GET when HEAD is rejected. Requests run sequentially with a 20-second timeout, at most three attempts and exponential backoff. Metadata JSON responses have a 2 MB bound. Each listing is attempted at most once per day.

Freshness locators must appear in the listing's reviewed evidence. Supported formats are JSON pointers (epoch seconds, epoch milliseconds, or ISO dates) and explicitly reviewed authoritative `http-last-modified` headers. A successfully checked landing page advances the public source availability date (`checked`) when no publisher date is stated. The public `metadata_reviewed` date continues to show when the seed metadata and starter query were reviewed. When a cadence is stated, a missing date or a date older than the cadence is flagged for review; unknown cadence does not imply staleness. A failed check retains the previous successful values. Older staged attempts cannot overwrite a newer attempt. Source responses and contact details are not retained. Freshness runs before the main collection gates under the daily lock. Its private-only SQL is written separately to D1; date-guarded upserts make retries safe and never modify canonical listings. A D1 failure is recorded in the daily receipt and log. A plan stages a private run artifact and does not write to D1.

`ops/regional-data-publications.json` is an intentionally empty template, not an automated matching rule. A link needs human review of the actual paper: the paper must explicitly name the exact dataset/release and describe its use. Keep the source URL and supporting passage in a private reviewed JSON array, with fields `dataset_id`, `paper_id`, `source`, `evidence`, and `reviewed: true`. Obtain current loaded listing inventories as private JSON arrays of objects with `id`; then stage locally:

```
python3 ops/regional_data_freshness.py --reviewed PRIVATE-REVIEW.json --datasets PRIVATE-REGIONAL.json --papers PRIVATE-PAPERS.json > PRIVATE-LINKS.sql
```

Review the resulting SQL and apply only through a separately authorized load. IDs must exist in the supplied inventories. This tool cannot verify the source passage or the inventories' freshness; the reviewer must do so. Link display separately requires both records to be visible. Never infer a link from a similar title, a related portal, geography, or publication date.
