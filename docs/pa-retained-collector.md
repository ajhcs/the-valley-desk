# Retained PA original handoff (fetching disabled)

The operator adapter accepts a supplied local original ZIP, unchanged genuine download receipt and acquisition envelope for the PA export candidate. It reuses the existing original import validator and export derivation. All three byte sequences are retained in a private content-addressed packet. Fixed relative basenames, hashes, sizes, private modes and the source configuration digest are verified before bytes reach the internal trusted intake. Hashes establish integrity; they do not authenticate who acquired a download. Unknown HTTP status, headers, response URL and redirects remain unknown.

Run npm run pa:retained with --mode retain, --candidate candidate-pa-export, --zip LOCAL_ZIP, --receipt LOCAL_RECEIPT, --acquisition LOCAL_ENVELOPE and --out PRIVATE_DIRECTORY. The destination must already exist under private Builder workspace build storage, be owned by the operator and have mode 0700. Packet files have mode 0600. Originals and manifests are never replaced. A replay can finish an interrupted partial packet; conflicting bytes stop the operation. Transfer the complete directory through authenticated SSH/SFTP while preserving private modes, then run --mode verify --packet PRIVATE_PACKET_DIRECTORY at the receiving Builder boundary. The verified result supplies owned bytes compatible with intakePaBrowserOriginal. This change adds no production caller or HTTP endpoint.

Retention/verification stay candidate operations. Accepted enrollment, access/configuration digests, source freshness and lease guards govern actual staging. Missing authority leaves evidence pending; the adapter cannot activate or publish. Replay does not renew a successful upstream-check clock. Export, acquisition, ingestion, source-check and bill/action/printer timestamps remain separate. Identical bill records in a later export represent snapshot refresh, not new legislative activity or enactment.

It documents hourly updates Monday-Friday and bill-update dates with links for each printer number, memos and amendments. This supports the ordinary session-link UI workflow used for the two retained, authorized cloud-browser downloads. It does not specify an unattended-client entitlement or explain the earlier refused bare HTTP request.

The [legal notice](https://www.palegis.us/legal) warns that web information does not replace official versions and offers no accuracy, timeliness or completeness warranty. No automation-specific condition was found in this reviewed notice or the data page. The [privacy policy](https://www.palegis.us/privacy-policy) concerns SMS/email subscriptions; it supplies no bulk-automation permission. These observations are bounded documentation findings, not a complete access-policy clearance or legal interpretation. Endpoint-specific robots/access conditions and the historical HTTP 403's cause remain unresolved. Do not relabel an unknown restriction as an explicit robots ban.

The refused client/route remains held. Fetch/URL acquisition modes are rejected, with no fetch implementation or automatic enable switch. Plumbob or Cloudflare egress is not substituted to overcome the refusal. Before any unattended source request, establish a publisher-supported acquisition arrangement for the declared client and hourly cadence: ask whether ordinary automated session-link downloads are supported, whether the prior 403 was an intended client restriction, and which bulk/feed interface or permission arrangement is supported if it was. No inquiry is sent by this adapter. Existing genuinely acquired captures can continue through offline retention and verification.

## Disabled end-to-end operational proposal

1. **Scheduling:** after access resolution and a reviewed dry run, install an explicitly approved disabled-by-default hourly weekday trigger in America/New_York. One acquisition at a time; bound each session to 120 seconds and each archive to the existing 2 MB limit. No timer, cron, service or listener is installed here.
2. **Acquisition and retention:** use only the established publisher-supported workflow, with an isolated context in an approved existing runtime. Preserve raw ZIP bytes, the collector's first-hand unchanged receipt and its checksum-bound acquisition envelope privately before closing the context. Record only observed response metadata; no status/header inference. Preserve unsuccessful observations without treating them as valid ZIPs.
3. **Authenticated handoff:** transfer the content-addressed packet over existing SSH/SFTP. Verify fixed filenames, configuration, exact bytes/modes/hashes, receipt binding and deterministic derivation at the receiving boundary. Transport authentication does not replace named acquisition-provenance review.
4. **Intake:** a separately reviewed operator caller must provide private durable retention and use the existing trusted intake and existing approved Worker/D1 operator authentication. The current Worker has D1, cron and nodejs_compat (compatibility date 2026-08-26), but no runtime intake caller, Browser binding or R2 binding. This candidate creates none. The application retains pending packets; accepted source enrollment is required for guarded review staging. Existing deterministic editorial gates alone govern later publication.
5. **Freshness and failures:** assess literal export age against a reviewed cadence policy; without one, freshness stays unknown. Preserve each bill's last-update/PN/action association and independently sourced later votes. A timed-out/denied/invalid/incomplete/regressed snapshot keeps prior dated evidence while exposing failure and age. Use bounded transient-failure backoff after the route is qualified; denial halts the source instead of changing egress. Replay cannot advance source-check success or create legislative activity.
6. **Rollback:** stop/disable only the new caller and schedule, preserving existing browser services and every immutable source packet. Retain source failure/unknown freshness in the UI. Revert adapter code separately; no evidence deletion or fabricated successful check.

## Cost and minimum decision

The proven existing Plumbob runtime and SSH/SFTP need no additional browser subscription for offline packets; host storage/compute consumption still exists and must be measured. No paid calls or new service are enabled.

Cloudflare is an architectural alternative requiring a browser binding/package and a reviewed raw-byte retention/intake path, rather than a workaround for the refusal. [Browser Run pricing](https://developers.cloudflare.com/browser-run/pricing/) lists 10 minutes/day and three concurrent browsers on Free; Paid includes 10 hours/month and ten concurrent browsers, with $0.09/additional browser hour and $2/additional monthly-average concurrent browser. [Workers Paid](https://developers.cloudflare.com/workers/platform/pricing/) starts at $5/account/month. Current plan, shared usage and incremental storage/Worker charges are unverified. Assuming one 30-second session each hour on 22 weekdays, browser time would be 4.4 hours/month and 12 minutes/day; it exceeds Free's daily allowance and fits Paid's included pool only if available. The 120-second session cap is a bound, not that assumed measured duration.

No new user decision is needed to prepare/review these offline packets. The smallest remaining decision for unattended operation is whether to pursue the specific publisher-support clarification above. Sending it needs an explicit instruction. After a supported route is established, review its bounded live test and the exact caller, retention destination and disabled schedule before deployment. General project access or user approval cannot override an access refusal.
