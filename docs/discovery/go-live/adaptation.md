# Orchestration, adaptation and acceptance

The plan fixes useful outcomes and factual boundaries. It leaves implementation means adjustable. The orchestrator can change a component, split a package or select a simpler delivery path when findings justify it. It cannot convert a failed check into a pass by quietly changing the expected outcome.

## Dispatch contract

Before starting a package, the orchestrator gives its owner:

- The exact source revision, selected worktree and relevant accepted dependency revisions.
- The package goal, acceptance IDs, source/model anchors and unresolved assumptions.
- Files the agent owns, shared interfaces it consumes and files it must leave untouched.
- Allowed tools and environments, source/acquisition authority and request/time/spend bounds when applicable.
- Required observable outputs, meaningful adverse cases, named independent reviewer and integration point.
- A small first increment that can reveal the main uncertainty before extensive implementation.

Sol owns schemas, collectors, query/API behavior, projection, migration and recovery implementation. Terra owns discovery research, source inventories, reader flows, coverage and operating measures, with focused implementation where assigned. Astra independently challenges evidence, identity/geography semantics, source/privacy boundaries, interface safety and observed outcomes. The orchestrator integrates and decides acceptance. These are model/agent roles, not invented staff identities or new operational permissions.

Use existing agents and their established model assignments when available. If new agents are explicitly authorized, select Sol/Terra/Astra for these bounded roles. A different model does not make a review independent if it merely repeats the author's assertions. The reviewer must inspect actual outputs and exercise discriminating cases.

## Package state and evidence

The package states are `not_started`, `in_progress`, `in_review`, `accepted` and `reopened`; a concrete external dependency can be recorded as `waiting` with an owner and next action. The package record keeps the observed fact and attempted remedies. A local pause in one package does not stop unrelated work.

Every acceptance record identifies the implementation revision, input/contract revisions, changed files, actual executed checks, limitations and reviewer disposition. Keep failed attempts and repaired findings. Tests, source observations, agent judgments and human reader observations remain distinguishable. A hash establishes which bytes were used; it does not establish an affiliation's truth or a reader's usefulness judgment.

All packages in this planning revision start `not_started`. Existing MP and WP acceptance is reusable only within its recorded inputs and scope. Do not overwrite a historical receipt to make it describe a later implementation. Record new acceptance and an explicit preservation comparison.

## Change classes and authority

| Class | Examples | Agent/orchestrator action |
| --- | --- | --- |
| Routine implementation | Component factoring, accessibility fixes, clearer copy, bounded query optimization, existing-library reuse. | Owner proposes or makes the local change; orchestrator accepts after relevant tests and independent review. Preserve the agreed behavior. |
| Evidence-driven design | Snapshot exceeds measured envelope; topics fail reader tasks; a source route is unavailable; a custom intake form costs more than a maintained link. | Open a decision with finding, alternatives, smallest viable choice, affected interfaces and rechecks. Orchestrator and Astra review the new means. Do not wait for a user decision already delegated. |
| Contract or acceptance change | New DTO/API version, changed query semantics, adjusted coverage denominator or predeclared performance envelope. | Revise the contract before its new run; preserve old results, reopen affected consumers and obtain independent review. A changed threshold cannot retroactively make an old failure pass. |
| Consequential scope/authority | Changing the nine counties or health-tech boundary, publishing uncertain identity, expanding source-use rights, adding paid services, actual outreach or deployment. | Prepare a concrete scoped proposal and verify existing session authority. Seek only a genuinely missing decision. Neither time passing nor a model output supplies approval. |

Public go-live language and paper-optional lean discovery are already selected by the user. Do not ask again whether the service needs a public pilot phase, complete creator dossiers or journal-linked code. The answer is no. Internal staging, tests and an isolated release rehearsal remain implementation methods, not a public product phase.

## Decision and finding loop

At the end of each meaningful increment:

1. Compare the actual output with the package's intended reader/operating result.
2. Classify the observed failure: acquisition gap, unsupported fact, identity ambiguity, review backlog, missing content, vocabulary/ranking, presentation or operations.
3. Record the source revision, case, expected behavior, observed behavior and evidence location.
4. Select the smallest repair that addresses the cause; explain why a simpler alternative is insufficient if adding complexity.
5. Identify affected dependencies and consumers. Mark their relevant acceptance reopened while leaving unrelated evidence intact.
6. Perform the repair, repeat the failed discriminating case and the relevant regressions, then request independent acceptance.
7. Update the next batch and package register. Keep an accountable follow-up for unresolved but nonblocking items.

A decision record needs the question, current evidence, alternatives, choice, assumptions, implementation owner, affected packages, recheck method and reconsideration trigger. Use concise entries in the execution decision register. Do not create a large dossier for ordinary component changes.

## Parallel work and integration

Reserve shared schema, router, Worker and generated catalog files before concurrent edits. Assign one owner to each interface and generated artifact. Other agents submit a patch proposal or wait at the contract boundary; they do not independently regenerate overlapping files.

UI agents can use valid shared fixtures while real collection proceeds, but those fixtures cannot establish coverage or source acceptance. Source researchers can prepare the next frontier while another batch is reviewed. GL08 can build correction handling against a small admitted slice while GL09 broadens the catalog. Integrate small changes and inspect actual public output before expanding the next slice.

At each integration checkpoint, the orchestrator checks that the generated data matches the reviewed manifest, public/private boundaries hold, original source values and historical evidence remain preserved where applicable, and the actual reader task succeeds. A reviewer finding returns to its owner with a precise failing case, not a request to make the report look successful.

## Repositories, libraries and skills

Keep the current Vite/React/TypeScript/TanStack Router/Cloudflare stack, Zod contracts and existing provider/storage modules as the default. Reuse the project's existing parsers and qualification code. Verify current official documentation before relying on an external API/library behavior. Do not install a new stack solely to execute this plan.

Use frontend testing/debugging for rendered journeys, product-design audit for observed usability problems, and CSE evidence/measure workflows for explicit acceptance questions. Read a selected skill when applying it. Source-access tools may supply factual observations where their output and permitted use match the source contract; a connector is not automatically a bulk collector or publication authority. Document unavailable tools and select an already qualified fallback before proposing installation.

Use a search or storage service only after a measured limit, an alternatives review and an approved cost/operating boundary. Keep optional embeddings, recommendations, graph databases, comprehensive people resolution, patents, full-text hosting, alerts and accounts outside the minimum launch path.

## Stop rules and escalation

A false person merge, materially false local attribution, private/sensitive-data exposure, publication-authority bypass, unauthorized source action, broken removal or unsafe rollback blocks the affected release. Preserve the finding and repair/retest. A failed critical reader task or required legacy consumer also blocks its launch scope.

An optional professional link, empty county, blocked optional source or cosmetic issue can have a reviewed follow-up. Record its user impact and coverage wording. A collection of optional gaps that destroys broad discovery is a product failure, not a reason to label each gap individually harmless. Astra and the orchestrator must assess their combined effect.

Escalate to the user only when an actual missing input or authority prevents further meaningful progress. Prepare the concrete choice and the work needed to assess it first. Continue independent packages, preserve unfinished work and report the remaining boundary accurately.
