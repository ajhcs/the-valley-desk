## Entry evidence required for each candidate

1. Identify the exact installation or provider, public endpoint and method, parser family/version and selected scope, including query/window, page bounds, denominator and expected content. Record the current first-party terms, API/access rules, robots rule where applicable, rate limits, rights and their dates/URLs. State the permitted purposes separately: one-time access, local raw retention, transformation, metadata redistribution, excerpts and continuing collection. Identify attribution/share-alike/deletion conditions and any ambiguity. An accessible community page does not itself prove that individual posts, attachments, personal data or all response fields have a reusable license.
2. Specify the exact one-shot public read and its maximum request count, response bytes, wall time and pacing, an accountable maintainer, review/expiry date, storage location and removal procedure. Credentials, paid access, alternate endpoints, follow-on pagination, redirects and production activation require their own authority; a response cannot expand the request scope. A rate-limit or access failure is a named gap, not empty coverage.
3. Identify the exact local parser input and complete raw-retention surface before sending. WP07 commits original response bytes only after its parser succeeds. WP12 and WP13 use conservative whole-response privacy and format gates, but these are not universal sensitive-content classifiers. A valid public page or directory can include people, health anecdotes, contacts, hidden markup, API keys or licensed third-party text. Process transient data in memory with bounded reads; do not persist a rejected body, secret-bearing header, provider-controlled error body or contact canary. If permissible raw retention or inspection itself is unclear, do not send.
4. Separate this review's source and parser assessments from WP03 truth. Qualified access cannot establish person identity, current employment, regional eligibility, clinical truth, source independence, editorial admission or measured recall. Provider-native identity, original source and account/person equivalence stay unresolved unless separately reviewed evidence supports them. Native forum edit/deletion consumption into current-claim invalidation remains a WP14 dependency; explicit rights revocation and scoped deletion are separately testable ledger actions.

## Required actual acquisition evidence

A successful real-source qualification needs an inspectable receipt for the **actual request**, not a synthetic response with a real-looking URL. It should bind the review decision and source/license evidence to:

- UTC request/response observation time, exact credential-free method and canonical endpoint, original/final URL and any rejected redirect; egress identity/version, DNS/connect-time public-destination enforcement and TLS host verification. Never include bearer tokens, cookies or user-specific secrets.
- Actual HTTP status and Content-Type (including charset when supplied), relevant safe pagination/rate headers and explicit absence when not supplied; declared content encoding and the exact bytes hashed. Distinguish wire-encoded bytes from the application-decoded representation delivered to the parser. The current `DiscoveryAcquisition` stores status, endpoint, byte count and representation hash; it does **not** carry MIME or general response headers. A source-specific, safely bound egress receipt is therefore needed for MIME rather than inferring it from a fixture or parser. WP06 exposes no native fetch fallback: the injected egress must enforce public destination at connect time, not merely precheck a hostname before an unrestricted fetch.
- Configuration/scope, source and parser version or content hash, exact permission/rights decision references and expiry, request and response SHA-256, byte ceiling and actual bytes read, request reservation/settlement, status and typed failure where applicable. Keep rate holds and uncertain attempts charged; do not infer that an abort refunded a request.
- Parser result and safe coverage gaps, plus storage/hash of the permitted raw representation and a literal source/version binding. Record unexpected MIME, redirects, parser refusal, incomplete pagination, access denial, forbidden or ambiguous rights as outcomes; do not rewrite failures as qualifications. Keep sensitive response material out of logs, public fixtures, provenance rationale, URLs and tracked files.

The two valid demonstration patterns must remain distinguishable. The strongest direct proof sends the approved real HTTP request through the actual WP06 transport and authorized local registry, records the actual response metadata at the controlled egress boundary, and commits the same parsed bytes through WP07 into an isolated local D1. Alternatively, a controlled one-shot capture can be hashed and later injected unchanged into local D1 for deterministic replay; that second step is a **replay**, not another network acquisition or evidence that native WP06 egress was exercised. In either pattern, verify the bytes and response status against the transport/evidence receipt and the resulting representation, lead and page; preserve source failures and raw-hash mismatch evidence. Temporary fixture capabilities or mock grants used to exercise the transaction must be labelled synthetic local plumbing and cannot prove provider permission, human authorization or production enrollment.

## Existing implementation limits

- The WP06 sample intake is a separate boundary: qualification expects an already retained representation, and `registry.qualify` checks its hash/configuration but does not invoke the provider privacy parser. The synthetic harness calls `appendRepresentation` before qualification. The WP07 collection parser gate therefore does not protect this earlier sample intake. Run the exact provider privacy/format preflight on the bounded in-memory sample before any `appendRepresentation` or durable body write; if it fails, retain no body and record only a safe failure.
- Source registry qualification binds its local configuration, rights/permission controls, sample endpoints and retained representations. It cannot independently verify the legal interpretation, provenance authenticity or real human decision represented by fixture capability resolvers. Replacing a real review with `allow` fixture controls is not qualification.
- Endpoint templates, budgets, leases and retention checks provide local enforcement, but DNS/connect enforcement belongs to the egress implementation. The existing synthetic tests have `envFiles: []`, `persist: false`, `remoteBindings: false` and closed egress; they prove neither live reachability nor provider terms.
- Forum qualification is limited to the versioned anonymous Discourse-shaped subset and category/topic ancestry. Provider responses with extra fields or unapproved contact/hidden data can fail safely; such a failure is format incompatibility, not provider outage. WP12 remains held until an actual installation and native edit/deletion consumer qualify.
- Institutional qualification requires a source-specific passive HTML mapping, exact endpoint and source date; active/hidden HTML, contacts, unexpected attributes, CSS and recovery diagnostics are rejected. The selected literal record and source evidence cannot be invented from an external identifier. A generic organization registry record or matching institution name alone does not instantiate a profile/roster, prove health-technology relevance, or establish current regional affiliation. The current transport does not bind MIME. Before the format guard, parse5 treated harmless JSON as text-only HTML: an unknown roster yielded a partial zero-record draft and a declared zero roster yielded a terminal draft. The corrected parser rejects JSON/plain text before capture, but does not validate HTTP MIME. Therefore explicitly verify the actual Content-Type and expected native format before invoking WP13; a no-record draft is not evidence that a JSON API was supported.
- `Content-Type` is not committed in the current WP06 acquisition schema and non-GitHub HTTP Link is not passed to provider parsers. Preserve evidence of these facts at the safe request boundary and do not represent missing authenticated metadata as validated continuation. Scope-wide revocation is not selective per-field cleanup; retained source contents and all dependent data must be removable according to the actual grant.

## Independent acceptance of a candidate

After the source-specific access and retention basis is reviewed, select only the preapproved endpoint and bounded scope. Inspect the local receipt and raw-hash binding, re-run the unchanged parser and actual isolated local-D1 composition against the exact approved bytes, and independently compare parser/version, counts, safe gaps and receipt fields. Test rejection for any unsupported response without retaining its contents. If the source representation falls outside the accepted parser or the rights basis remains unclear, record `blocked` or `unsupported` with a redacted reason; do not adapt the source response, pretend it was natively parsed, broaden the URL, or use a successful empty result as coverage.
