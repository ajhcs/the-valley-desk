Implementation candidate for independent review and orchestrator disposition. ## Storage and API boundary

`src/content/discovery-evidence.ts` defines strict versioned inputs and the injected capability interface. `createDiscoveryEvidenceStore` in `src/ingest/discovery-evidence-store.ts` exposes control/origin/representation/evidence/claim/decision writes, explicit observations and refresh failures, separate private notes, reviewed retention revocation, exact-revision reads and origin counts. No HTTP handler, network transport, scheduler or public DTO is introduced. Default `schemaVersion` is the accepted `discovery-v1`; a supplied unsupported version fails. Root owns package scripts, schema-version integration, receipts and acceptance status.

The resolver is trusted server code: it receives an opaque token and the operation/action/target plus full canonical request digest, and returns a verified capability receipt. A client authority string or schema-shaped decision cannot authorize a mutation. The receipt must bind the exact request and expressly permit the specified minimal audit metadata. The resolver fixture is synthetic and authenticates no human. Actual identity, origin checks and protected HTTP mutation integration remain WP14/WP16 work.

Control values are identifiers/tokens, not prose or source excerpts. Permissions explicitly bind enrollment/configuration revisions and a strict material scope, with separate fetch/retain/transform booleans. Rights bind the same material scope. The scope is either a genuine artifact/version/material or an explicit source-response scope binding source, installation, enrollment/configuration, endpoint constructor/template digest, reviewed request-scope digest and permitted response material. It cannot silently reinterpret an unknown work as an artifact. Captures require both current scoped permission and rights. These rights records are affirmative private retention/transform grants, not the general public artifact-rights assessment. Initial denial is represented by denied permission or an absent grant; a later denial requires the audited removal path. Appending retain:false or transform:false is rejected so an assessment cannot leave earlier protected content behind. Public unknown/denied/reuse/display assessments remain separate WP14 work. This private scope is not a reuse/display license or independent permission finding.

## Bytes, transforms and exact evidence

Representations retain bounded supplied `Uint8Array` values in D1, avoiding an external-object atomicity claim. They separately preserve SHA-256 of supplied bytes and of UTF-8 serialization of normalized text. `captured-body-bytes` identifies bytes supplied by trusted transport; it does not claim compressed HTTP wire capture. `utf8-reencoded-text` remains explicitly labeled and never becomes captured body bytes. Evidence retains that distinction.

The installed supported transforms are `text-or-json-v1` and `utf8-nfc-lf-v1`: fatal UTF-8 decode, CR/CRLF to LF, then Unicode NFC for normalized text. Parser and normalizer references and implementation tokens are pinned. Unsupported transforms, invalid UTF-8/JSON and mismatches fail. Exact spans use UTF-16 offsets into this retained normalized text, including surrogate-pair boundary checks. Structured pointers use the original decoded JSON before NFC normalization: distinct original keys stay distinct, duplicate raw keys fail, and pointer traversal accepts only own JSON properties and valid RFC6901 escapes/array indices. Non-JSON values, sparse/accessor arrays, cycles, inherited objects and nonfinite numbers fail rather than being silently coerced. Record snapshots are cloned before the asynchronous capability resolution, so caller mutation cannot change a signed request.

A later capture with changed bytes creates the next immutable representation revision. Unchanged bytes within the same family require `observeRepresentation` referencing the already retained revision; they do not duplicate a representation identity. An A→B→A return to identical bytes observes retained A. Observation timing and failed refresh timing are explicit records; a failed refresh does not renew health or silently remove permitted evidence.

Evidence pins exact representation revisions and both digests. Claims coexist under separate IDs, preserve subject/predicate/value/uncertainty/time bounds/policy and exact evidence digest vectors. Decisions retain the selected claim, evidence and digests, server-created authority, expected subject/head bindings, rationale, policy and superseded decision. A stable scope binds one decision family to one subject/predicate; corrections can select a contradictory claim without changing scope. `withdrawn` is a private history disposition, not an extra accepted WP02 public decision state. Private notes use a separate record/table row and are not embedded in claim fields.

## Origins and reviewed changes

A reviewed origin revision has a stable original-work identity, explicit rights owners for its source-bearing rationale, reviewed member IDs and exact member→endpoint bindings. Capture names a member and must match the reviewed endpoint in both preflight and the D1 commit guard. An origin's rights ownership must cover the capture's artifact/version/material; matching a grant revision alone is not the identity rule. Three mirrors of one original produce one origin count.

A reviewed origin revision replaces its complete active member set and invalidates all transitive dependents of the superseded revision. A retired revision has an empty member set and accepts no captures. Full merge can retire B before transferring its actual members into A; a later split releases the members before a new reviewed family acquires them. No fabricated spare member is required. Membership and decision-scope identities reject direct UPDATE/DELETE/REPLACE rebinding. Endpoint text lives only in removable content; the membership ledger retains identifiers only.

## Atomicity, currentness and replay

Each mutation uses one real D1 batch: insert the guard, append immutable metadata and protected content, append exact dependency edges, perform the operation's extra writes, advance the head, append a durable outcome, then erase the transient guard. SQL validates expected heads, scope/rights permission, capability/action/request binding, original content binding and final outcome. Prefix writes, failed final statements and concurrent stale revisions abort the whole batch. Canonical request hashes reject conflicting reuse of an operation ID. A replay resolves the existing durable identity; response availability fields reflect current tombstones/expiry rather than asserting that erased content remains retained.

Every new use checks complete ancestor availability, invalidation and expiry inside the transaction. Source authorization ancestors (`rights`, `permission`, `enrollment`) must still be their pinned current heads. Historical representation/evidence/claim/origin revisions need not equal their latest family heads, preserving exact historic evidence after an unrelated byte change. Configuration/parser/normalizer revisions remain captured history after the initial current-head capture check. New claims/decisions separately require the current policy and catalog subject revision. Commit expiry uses the later of actual SQLite time and the trusted injected server clock, and is checked again at the durable outcome.

Grant renewal does not silently rebind old evidence to another approval. The current private implementation fails closed when a pinned source authorization is superseded. An explicit reviewed requalification/binding path is a named WP14 integration requirement. This is not full public WP02 dependency-vector qualification. Reads report `usable` and `expired`; expired ancestry withholds content. Other invalidated history remains private audit history, not usable corroboration.

Durable operation audit retains only the approved operation/request/content hashes, IDs, capability receipt ID/hash, scoped principal/authentication-context IDs, action and commit timestamp. Tokens and capability bodies are transient; source excerpts and reasons are never stored in replay outcomes. Durable capability receipt hashes are checked against the same pending guard before acknowledgment. A structurally shaped acknowledgment outside this server/database boundary is not persistence proof.

## Bounded coherent read integrity

`DISCOVERY_EVIDENCE_READ_LIMITS` explicitly bounds each read to 512 distinct ancestor revisions and 4,194,304 UTF-8 bytes of ancestor content. One SQL observation selects the target's availability/head/expiry flags and qualified ancestor payloads from the same database snapshot. The recursive CTE stops at the 513th ancestor to detect excess; SQL computes the byte/count bound before transferring ancestor bodies. Exceeding either limit throws `discovery-evidence-ancestor-bound`, never a partial usable result. The read linearizes at that SQL observation; a later revocation can follow the snapshot and does not make it a timeless permission claim.

Every retained ancestor's canonical content SHA-256 is recomputed. Representation ancestors additionally verify actual retained byte values and digest, supported transform versions, normalization reproduced from bytes, normalized-text digest and original structured JSON. A mismatch returns `quarantined:true`, `usable:false`, `content:null` for the affected revision and its dependent read, without modifying immutable history. New ref-consuming writes perform this integrity validation, while their D1 transaction separately enforces current heads/rights/expiry and exact binding; SQL does not compute SHA-256. Replay acknowledgments report current quarantine state. Fixtures bypass and restore the immutable UPDATE trigger only inside isolated D1 to simulate corrupted imports. This protects against accidental corruption/import mismatch, not an adversary coherently rewriting the entire database and its audit records.

## Explicit retention removal

Revocation requires fresh scoped server capability, a current policy and a CAS check of the identified rights family's actual current head. The requested historical grant identifies the exact canonical discriminated material scope; every rights revision of that scope is included, including newer grants. Expired source authorization is removable: expiry blocks new uses but cannot block authorized erasure.

The transaction removes all protected content in the rights-owned forward dependency closure: representation bytes/text/structured values, evidence quotes, claims, decisions and rationales, private notes, observations/failure content, and source-bearing origin rationale on every owned revision, including an origin never consumed by a capture. It erases the revocation reason itself because it could quote forbidden material. Tombstones/invalidation and the epoch update commit atomically. A canonical scope-hash tombstone prevents new capture under another grant ID; old operation replay returns a tombstoned receipt or fails and never restores content. New affirmative rights or permission IDs in the same withdrawn scope are rejected with `discovery-evidence-revoked-scope`; they cannot reopen source-bearing origin rationale retention. There is no regrant path in this package. Only the separately permitted audit identifiers/hashes remain. This path requires an explicit minimal-audit grant and does not invent legal permission to retain a hash.

Shared enrollment/configuration/parser/policy controls do not become deletion roots. Unrelated material under the same source controls remains usable. The abandoned reverse-connected-component prototype did erase unrelated content and missed a newer unused rationale; those failed independent probes are retained. Explicit source-bearing rights ownership replaced it.

WP04's content-bearing decision/alias/relation bridge fails closed for WP05 anchors until a reviewed projection/removal bridge exists. Both insertion orders are guarded: prior catalog anchors block WP05 evidence registration, and later catalog decisions, aliases and relations cannot consume WP05 evidence. Safe ID anchors alone do not establish usable evidence. Generic legacy metadata is not automatically asserted to contain or authorize WP05 source content. WP14/WP16 must maintain the complete removal and public-projection contracts before enabling that integration.
