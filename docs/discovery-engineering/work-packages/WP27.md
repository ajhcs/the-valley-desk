## Purpose and entry conditions

Release only a concrete reviewed candidate, then assess actual public operation. Maps to R01–R18, P01–P32 implementation assumptions, E01–E06 and model anchors `C_DELIVERY`, `VIEW_PORTAL`, `F_PUBLISH`, `F_DISPLAY`, `F_REFRESH`, `F_COVERAGE`. WP24 supplies empirical and preproduction E06 results; WP25 supplies the isolated, enrolled preproduction operating pilot; WP26 supplies recovery rehearsal. None requires this public release to have happened first.

A separate mandatory entry condition is explicit scoped operational release authorization covering the exact candidate, environment, migration, bindings, enabled source scopes, cutover window and rollback limits. Engineering acceptance, a plan dependency or prior deployment permission does not itself authorize these operations. Prepare the exact reviewable candidate and release packet before requesting any missing release authorization. Actual collection, editorial publication, service registration and legacy retirement retain their distinct boundaries.

## Release contract and sequence

1. Assemble exact source SHA, dependency lock hash, build artifact hashes, schema/migration sequence, revised model/contracts, frozen policy versions and full evidence index. Reconcile WP24/WP25 results against that candidate; material changes invalidate affected receipts. Identify unresolved inputs without treating them as accepted risk.

2. Independently verify final required CI conclusions on that SHA, all six source routes, independent people/paper support, compatibility consumers, retention, observability, operating ownership and recovery target. Preserve current PDF, build, scheduled-smoke, dependency-audit and secret checks. Record deployment tools and unavailable runbooks explicitly.

3. Prepare restoration and rollout commands with reviewed bindings and stopping thresholds. Confirm backup/restore rehearsal and data compatibility; do not imply a code rollback reverses an irreversible migration. Keep additive legacy support and leave WP28 retirement unexecuted.

4. Obtain or verify scoped operational authorization for the prepared packet. An authorized release operator executes only that packet, retains step receipts and stops on revision/binding drift, migration failure, critical attribution/privacy failure or unavailable recovery. Provider schedules start only within their separately qualified and authorized scopes.

5. Read back deployed identity and served behavior after deployment. Check person, organization, paper, project, code and discussion journeys; current versus historical regional labels; evidence/rights; independent sources; canonical/crawler metadata; protected review paths; legacy feeds and Watch routes. Test permitted correction/invalidation behavior without inventing live editorial authority.

6. Retain the observed window, actual source-health and coverage denominators, error/latency signals and operator handover. Distinguish deployment success from public operational acceptance; failure triggers the approved stop/rollback route and remains a failed receipt.

## Acceptance criteria

1. **AC-WP27-01:** Given the release packet, each prerequisite receipt binds to the exact candidate or an explicitly justified unchanged component; evidence is the independent traceability review.

2. **AC-WP27-02:** Given missing scoped authorization or environment drift, execution stops after preparation; evidence names the unapproved action and responsible authority.

3. **AC-WP27-03:** Given authorized deployment, recorded source/build/schema identities match served identities; evidence is timestamped deployment and readback receipts.

4. **AC-WP27-04:** Given public journey and protected-route probes, required semantics and legacy compatibility hold without private-field leakage; evidence is redacted public acceptance observations.

5. **AC-WP27-05:** Given a stopping-threshold breach, operators use the rehearsed recovery path and preserve failed evidence; evidence is a recovery receipt and resulting-state verification.

6. **AC-WP27-06:** Given the acceptance window, the accountable operator accepts or rejects public operation separately from preproduction E06; evidence is a dated operational decision and residual-gap register.

## Future validation and handoff

All release actions are future-only. Hold failed empirical gates, unsustainable pilot findings, unverified recovery or missing operational inputs. Hand accepted operation to the named owner; WP28 and WP29 remain separately scoped. Future CSE `plan-engineering-evidence` and `develop-operational-scenarios` skills support reviewable release/recovery evidence, not deployment authority.
