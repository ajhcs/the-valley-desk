## Readiness and sanitized failure diagnostics

The local readiness repair is based on `a6f99aff245e0dc370d41f80cd2ae900e81f97b5`. The prior runtime attempt failed before click in 0.805 seconds with `ValueError: ordinary-page-evaluation-refused`; its discarded exception details do not identify the cause. Offline execution of the original SNAPSHOT with `document.body === null` reproduces a TypeError. That proves a controller defect, **not** that the live failure had a null body, or that it was a publisher refusal. The historical HTTP 403's cause remains unknown. All eight private failed-preflight originals are preserved unchanged.

SNAPSHOT and CLICK now tolerate a null body while observing title/widget denial and interstitial indicators. After the owned target's expected navigation, readiness polling has one aggregate **10-second** budget, at 100 ms intervals, inside the existing overall attempt deadline. Waiting is permitted only for the initial `about:blank` transition before the expected page commits, or construction of the exact expected `/data` page until a body exists and readyState is `complete`. A complete page with no unique exact anchor fails immediately; this wait does not retry source acquisition, exceptions or missing links. A later `about:blank`, unexpected URL, observed redirect, actual challenge/denial or browser interstitial stops immediately. CLICK rechecks complete body/readiness and the exact anchor; post-click observations have no readiness grace period. One click and owned cleanup/download cancellation rules remain unchanged.

An owned failed attempt retains a private immutable `failure.json` with schema `pa-browser-failure-1`, outcome `held`, and `liveResumeAuthorized: false`, before owned cleanup. Outer timeout/CLI handling preserves the first failure rather than replacing it. Fixed categories distinguish `evaluate-exception`, `protocol-error` (including a per-CDP command timeout), `readiness-timeout`, `denial-or-challenge`, `interstitial`, `redirect-or-unexpected-url`, `protocol-status-refusal`, `missing-or-ambiguous-exact-link`, `exact-link-binding-refusal`, `click-refusal`, `attempt-timeout`, `attempt-cancelled` and a conservative `internal-error` fallback. Unknown reason text is replaced by `unrecorded-detail`; exceptions never authorize continuing.

The receipt stores only bounded readyState/body presence, URL classification, denial/interstitial indicators and expected candidate link count (capped at 1,000). An actually observed owned root-frame Document response may add a classified URL and numeric HTTP status; absent observations remain null. This is page/document protocol evidence, not inferred download response metadata or a source-health update. Evaluation errors retain only allowlisted exception classes and fixed detail codes such as `null-property-access`, `undefined-property-access`, `undefined-reference`, `security-error`, controlled click-guard codes or `unclassified-exception`; CDP errors retain only a bounded numeric code. Arbitrary exception/page text, raw DOM, raw URLs/query credentials, headers, cookies and authentication data are excluded. An evaluation failure before any valid snapshot leaves page state null instead of reconstructing it. Failed readiness/evaluation/refusal attempts create no acquisition success marker and do not enter source intake.

Socket-free fixtures execute the actual exported JavaScript in Node's VM, including null-body/initial navigation, delayed construction, pre/post-body challenge, interstitial/redirect, exact-link and click cases. Python attempt fixtures exercise the same expressions, sanitized exception/protocol receipts, timeout and owned cleanup. These readiness fixtures use the existing Node runtime in addition to Python stdlib; no browser/network/dependency installation is involved. No live qualification, production caller, schedule, enrollment, health renewal or deployment is performed by this repair.
